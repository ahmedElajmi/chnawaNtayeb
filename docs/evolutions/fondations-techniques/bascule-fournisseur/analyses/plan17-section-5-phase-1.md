## 5. Phase 1 — Contrats métier, indépendance fournisseur, SQL

Objectif : **délier le domaine du fournisseur de données** et valider la couche SQL
(mécanismes). **Architecture de stockage validée (décision du chef)** : **un seul
fournisseur actif à la fois** — Firebase aujourd'hui, SQL demain, **aucun mode hybride**
(aucune répartition de collections, aucun routeur), sélection centralisée au démarrage
(`DATA_STORE=firestore|sql|memory`) ; **aucune migration en production en phase 1** —
la bascule est **globale et unique**, différée et soumise à une **décision explicite**
(§ 12) ; la phase 1 construit l'indépendance (contrats, adaptateurs, mécanismes) et
**n'écrit pas d'adaptateurs pour les domaines métier** dont les modèles ne sont pas
encore stabilisés (recettes, ingrédients, frigo — leurs évolutions de modèles
interviennent après la bascule, directement sur SQL). **SQL est une famille de bases
relationnelles, pas un moteur désigné** : aucune cible SQL privilégiée ; fonctionnalités
SQL **standard** et structures relationnelles **portables** privilégiées ; toute
spécificité moteur isolée dans son adaptateur (solution de remplacement ou limitation
documentée) ; différences de types, JSON, index, transactions, contraintes, pagination,
concurrence et migrations analysées **pour chaque moteur concerné** ; le choix du moteur
définitif est **différé** et exige une **décision explicite**. SQLite est le moteur
actuellement **réellement testé** (harnais) ; le harnais est **extensible à tout moteur**
sans modifier le métier. Règle permanente : `CLAUDE.md`
(§ « Compatibilité permanente Firebase / SQL »).
