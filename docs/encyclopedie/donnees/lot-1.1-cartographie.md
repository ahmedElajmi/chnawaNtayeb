## 3. Contrat `DataStore` et implémentations

`server/storage/types.ts` — le contrat unique de toutes les routes (aucune route ne touche la base autrement) :

| Opération                     | Usage réel vérifié                                                                                                                                                                                                                               |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `changes(name, since, limit)` | change feed loti (`dataRoutes` via `gateway.computeChanges`), cache pays (`app.ts`), politique mot de passe (`policy.ts`), lecture thèmes (`adminDataRoutes`)                                                                                    |
| `findFirst` / `findWhere`     | annuaire comptes (e-mail), versions d'un item (`/where`, `canManage`)                                                                                                                                                                            |
| `page`                        | annuaire comptes paginé avec **total juste** (`/admin/api/accounts`)                                                                                                                                                                             |
| `get` / `ids` / `maxRevision` | lectures unitaires ; `ids` alimente le `replace` (marqueurs de suppression)                                                                                                                                                                      |
| `put` / `remove`              | écritures **complètes sans fusion** ; suppression = marqueur `{ deleted: true, revision }`                                                                                                                                                       |
| `commit(ops, guard?)`         | lot atomique conditionnel : publication atelier (public + copie + version, garde `written_at`), publication réglages (doc + version), création de compte (`users`+`auth`+`email_index`, garde `taken=null`), historique courses (entrée + index) |
| `transact(name, id, op)`      | fusion du frigo (2 appareils simultanés ne s'écrasent jamais) — `kitchenRoutes`                                                                                                                                                                  |

**Implémentations** (toutes tenues au harnais `server/storage/contract.ts` — `describeDataStore`) :

- `firestoreStore.ts` — branchée dans `server/app.ts` (Admin SDK, règle d'identifiants et `revision`/`deleted` conformes aux règles) ;
- `memoryDataStore.ts` — `LOCAL_MEMORY_STORE=1`, **refusée en production** (garde dans `app.ts`) ;
- `sqlStore.ts` (Knex) — **écrite et testée sur SQLite** (`sqlStore.test.ts`), non branchée (commentaire d'en-tête : « NOT wired yet »).

**Statut du store SQL générique (décision du chef)** : ses tables uniformes (`id / data /
revision / deleted`) sont un **artefact de test uniquement** — harnais de contrat et
environnement local, **jamais la production**. Le **schéma SQL de production** sera une
**modélisation relationnelle par domaine** (tables dédiées, colonnes typées, clés,
contraintes, index), conçue à la migration, moteur-agnostique, et implémentant le
**même contrat** `DataStore` ; **jamais de documents JSON en colonnes** comme
persistance (JSON réservé aux échanges API, imports/exports, sauvegardes ; toute
exception validée explicitement — **aucune exception considérée comme validée
implicitement**). La forme finale du harnais (générique maintenu en test-only, ou
pilote relationnel démontrant le mappage sur une collection stable) est soumise à
l'**arbitrage n° 7** du dossier du lot 1.2 — décision du chef.

Le filigrane en mémoire (`watermark.ts`) n'est **qu'un raccourci** : un redémarrage le vide, la correction ne s'appuie jamais dessus (premier poll recalcule le delta réel).

## 4. Carte des flux (écriture → diffusion → copie client)

**Écritures (toutes passent par le serveur, identité prouvée)** :

1. **Catalogue public** (`recipes`, `ingredients`, catégories, `units`, `countries`) :
   - édition directe backoffice : `PUT/DELETE/POST /api/data/:name…` (`canPublish`, parseur du registre, lot ≤ 200) ;
   - workflow de validation : `/admin/api/workspace/save` (copie, garde `written_at`) → `/admin/api/workspace/publish` (**un seul `commit`** : doc public + copie + version) → `/unpublish` (marqueur + copie).
2. **Réglages** : `/admin/api/settings/publish` (version courante exigée = anti-écrasement mutuel ; commit doc + version) ; `/admin/api/settings/polling` (super admin seul, bornes 15–600 s).
3. **Comptes** : `/api/auth/register` et `/admin/api/employees` → `createAccount` (hash **avant** toute écriture, `commit` atomique `users`+`auth`+`email_index` avec garde d'unicité e-mail).
4. **Frigo** : `POST/GET /api/kitchen` (`transact` : lecture-fusion-écriture sérialisée, tombstones purgeables), `/api/kitchen/history` (`commit` entrée + index, plafonds par compte).
5. **Politique de mot de passe** : `/admin/api/password-policy` (`settings/password`, super admin).

**Diffusion vers les clients** :

- `POST /api/data/changes` : **un seul appel répond à toutes les collections suivies** (le client liste ses révisions) ; chemin rapide par filigrane = **zéro requête base** pour un client à jour ; accès `public` pour les visiteurs, `admin` pour les prouvés (collections `read: 'admin'` exclues sinon) ; collections `read: 'server'` **jamais servies**.
- `POST /api/kitchen` (push débouncé après chaque modification) / pull à l'ouverture, à la connexion, au retour de visibilité (≤ 1/min).
- Écritures suivies d'un `raiseWatermark` (le filigrane monte au fil des écritures).

**Copies côté client** : cache IndexedDB par collection (`SyncedCollectionStore`, rattrapage incrémental par `revision`, marquage `deleted`, relecture complète après 30 jours hors ligne) ; frigo local localStorage (`local` sans compte) ; poller unique regroupant les suivis (`fetchPollingInterval` configuré en backoffice, servi par le serveur).

## 7. Écarts et observations (registre ↔ règles ↔ usages)

Aucun écart bloquant ; constats documentés, **aucune action dans ce lot** :

1. **`settings` : parseur registre `null`** (`parse: null as unknown as ParseDoc`) — collection multi-documents aux formes hétérogènes (`polling`, `password`, `matching`, `review`), chaque lecteur revalide le sien (`adminDataRoutes`, `auth/policy.ts`, résolveurs du domaine). Cohérent (accès `server`, jamais servi par les endpoints génériques) ; pour la conversion SQL : **une table, validation par lecteur** — à prévoir en 6a.
2. **Les règles Firestore utilisent `request.auth`** (custom token `superAdmin`, existence `admins/{uid}`) alors que **l'application n'émet jamais de token Firebase Auth** (aucun SDK client ; sessions signées par le serveur, cf. commentaire `firebaseAdmin.ts`). Les règles sont donc une couche de **défense en profondeur** contre tout accès client direct (utile), effective uniquement via le contournement Admin SDK du serveur. Pour la phase SQL : l'équivalent de ces garanties est **le contrôle serveur déjà en place** (`resolveIdentity`, `writable()`, parseurs, plafonds) — le fichier de règles n'aura pas de traduction directe, sa suppression sera une décision de 6a.
3. **Écritures par lot non atomiques entre documents** : `POST /api/data/:name` (import ≤ 200), `/api/data/:name/replace` et `/admin/api/workspace/import` écrivent séquentiellement (chaque document atomique, le lot ne l'est pas). Comportement à **préserver tel quel** dans les contrats de 1.2 ; toute amélioration (commit atomique large) sera une décision séparée du chef.
4. **`server/seo.ts` duplique la logique de synchronisation incrémentale** hors de la couche storage (copie maison + suivi de révision) — c'est le principal coût technique des touchpoints ; le port de 1.2 le résorbe sans changer le rendu.
5. **Contrainte de ids de thèmes** : `firestore.rules` interdit la création des ids `classique`/`fkhar` (thèmes intégrés) ; cette contrainte n'existe **pas** au registre (elle est du ressort des règles). À conserver côté serveur lors de la transition SQL (note pour 6a).
6. **`pageLimit: 0` des collections `server`** : double garde redondante avec `read: 'server'` (jamais servis par le change feed de toute façon). Cohérent, aucune action.

## 8. Architecture de stockage validée (révision — décision du chef)

La décision 🚩 initiale (« ordre des domaines migrés ») est **close sans choix** : elle
est **caduque**. L'architecture validée retient **un seul fournisseur actif à la fois**
et une **bascule globale et unique** — aucune répartition de collections, aucun
routeur, aucun mode hybride en fonctionnement normal.

- **Modes exclusifs** : `DATA_STORE=firestore` (actif) · `DATA_STORE=sql` (future
  bascule) · `DATA_STORE=memory` (local seulement, refusé en production) — sélection
  centralisée au démarrage dans `server/app.ts`, un adaptateur pour toute
  l'application ; le changement de fournisseur ne modifie ni le métier, ni les
  routes, ni les interfaces.
- **Bascule globale = transformation relationnelle** : les documents sont transformés en
  **structures relationnelles** — tables dédiées par domaine, colonnes typées, clés
  primaires/étrangères, contraintes d'intégrité et d'unicité, index — avec les modèles
  logiques **actuels** (aucune évolution sémantique 5b dans cette opération) ;
  **jamais de documents JSON en colonnes** (JSON réservé aux échanges API, imports/exports
  et sauvegardes ; toute exception validée explicitement) ; **l'évolution des modèles est
  séparée** du changement de fournisseur et s'applique **après**, directement sur SQL
  (DDL, backfills, comparaison avant/après, opération inverse) — les deux transformations
  ne sont **jamais cumulées**. Le retour arrière exige la **transformation inverse**
  (SQL relationnel → documents Firestore), conçue et démontrée en 1.5.
- **Transition** : gel des écritures → **export complet** (révisions et marqueurs de
  suppression compris) → import → **comparaison exhaustive zéro écart** → bascule de
  la variable d'environnement → dégel ; **jamais de double écriture** ; le delta
  incrémental reste documenté comme optimisation conditionnelle, admissible
  seulement une fois le curseur composite `(revision, id)` démontré.
- **Retour arrière symétrique** (export SQL → import Firestore) tant que non clôturé,
  **démontré — pas seulement décrit — dans deux scénarios** lors de la répétition
  générale **1.5** (hors production) : A, retour immédiat ; B, retour après usage réel
  de SQL — y compris le cas de **monotonie des révisions** après un retour tardif
  (l'adaptateur estampe alors à `max(horloge, maxImporté + 1)`).
- **Moteurs SQL — SQL est une famille, pas un moteur désigné** : le choix du moteur
  définitif (PostgreSQL, MySQL, SQL Server, autre) est **différé** et exige une
  **décision explicite** (besoins, coûts, hébergement, performances, contraintes). Les
  fonctionnalités SQL **standard** et les structures relationnelles **portables** sont
  privilégiées ; toute spécificité moteur reste **isolée dans son adaptateur**. Statuts
  réels : SQLite **réellement testé** (harnais de contrat) ; **tout autre moteur —
  PostgreSQL, MySQL, SQL Server — non démontré tant que sa suite de tests pertinente
  n'est pas passée** ; le harnais est extensible à tout moteur **sans modifier le
  métier** ; les tests distinguent les garanties communes du contrat des particularités
  de chaque adaptateur (matrice de capacités par moteur en 1.4).
- **Nettoyage post-bascule** (ex-lot 1.6) : retrait de l'adaptateur Firestore après
  clôture, analyse d'usage (§ 31 V12).
- La contrainte technique dure reste vraie mais sans effet de séquencement :
  `users` + `auth` + `email_index` sont toujours écrites dans **un même `commit`** —
  la bascule globale transporte **tout** le registre en une seule opération.
