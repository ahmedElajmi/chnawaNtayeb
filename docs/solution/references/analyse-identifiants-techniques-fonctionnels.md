# Analyse architecturale — identifiants techniques et fonctionnels des modèles

**Statut : annexe au dossier d'exécution F1 v5** (`lot-F1-execution-dossier.md`), soumise à la
revue du chef. **Référence architecturale — pas une autorisation de refonte des modèles
existants** : elle ne modifie aucun modèle, aucun lot ; les écarts notés sont traités dans
leurs lots respectifs (6a, F4, CMS). Strictement documentaire — aucune modification de code,
aucun commit. **Application des bornes d'identifiants** : les limites évoquées ici ne sont
pas de simples mentions — les bornes structurelles du stock (longueur d'id d'entrée, cap de
section) sont **exécutées** par `validateStockEntry` (dossier v5 § 4.5 et § 5), côté client
comme côté serveur.

## 1. Principe adopté (consigne du chef)

Pour toute entité persistante ayant besoin d'une identité propre :

- **`id`** : identifiant **technique** — stable, unique, immuable, jamais dérivé d'une valeur
  métier modifiable.
- **`code`** : identifiant **fonctionnel facultatif**, créé seulement s'il apporte une réelle
  valeur métier (jamais par anticipation).
- Les autres attributs métier restent directement dans leur modèle.

Règles retenues : un identifiant technique ne change jamais ; les relations utilisent
**toujours** les identifiants techniques (`ingredient_id`, `recipe_id`, `user_id`…) ; emails,
téléphones, codes métier et slugs ne remplacent jamais un identifiant technique dans une
relation ; clés primaires composites autorisées quand elles correspondent à la nature de la
table d'association ; contraintes d'unicité définies sur les champs concernés et garanties **au
niveau du stockage serveur** (Firestore : garantie transactionnelle — le mécanisme `commit`
avec garde existant ; SQL : `UNIQUE`), jamais seulement par le frontend.

**Ce principe ne déclenche aucune refonte** : les modèles existants sont analysés tels qu'ils
sont ; seules les incohérences réelles sont notées, avec leur lot de traitement.

## 5. Modèles futurs / conditionnels (ni construits ni anticipés)

- **Plusieurs emails ou téléphones par utilisateur** : le modèle évoluerait alors directement
  (table `user_emails` à clé composite, `UNIQUE(email_normalisé)`) — aucune abstraction
  anticipée aujourd'hui ; l'`uid` reste l'ancre de toutes les relations (évolutivité visée par
  le principe § 1, déjà satisfaite).
- **Réservations de stock** : hors F1 (B-F1-6 ✅), réexamen F3/E5.
- **Codes-barres / références externes** : à la demande réelle, évolution ciblée du modèle
  concerné (colonne + `UNIQUE` éventuelle), jamais une table universelle.

## 6. Impacts sur la future migration SQL 6a

1. **Aucune dette nouvelle créée par F1** : `StockEntry` respecte le principe (id technique,
   référence technique, pas de code fonctionnel) ; la table 6a `fridge_entries` (dossier
   fonctionnel § 8) a pour clé primaire **composite** `(account_id, id)` — conforme à la règle
   3.1.5 du chef.
2. **Unicités à garantir côté serveur en 6a** (déjà absentes ou seulement implicites) :
   `recipes.slug` UNIQUE (aujourd'hui dédoublé côté client seulement) ; `units.label` UNIQUE
   (aujourd'hui garanti par la construction de l'id, pas par contrainte) ; `users.email`
   UNIQUE (déjà garantie par la réservation atomique — deviendra une contrainte `UNIQUE`
   native) ; `users.phone` UNIQUE **si et seulement si** F4 décide la règle « un compte par
   numéro » ; `ingredients.code` UNIQUE si un code fonctionnel réel est un jour introduit.
3. **Normalisation email** : la convention actuelle (trim + minuscules à la création, forme
   relue côté serveur, comparaison insensible à la casse par stockage normalisé, conflit
   d'inscription rejeté par la garde atomique) est **exactement** ce que demande la règle
   3.2 — rien à changer ; elle sera traduite en 6a par une colonne `email_normalisé UNIQUE`
   (ou une collation CI + index fonctionnel selon le moteur, décision propre à 6a).
4. **Tables d'association à clés composites** (nature d'association) : `recipe_ingredients`,
   `plan_meals`, `fridge_entries(account, id)` — aucune table universelle, aucun JSON
   substitut (règle permanente).
5. **Référence des unités par libellé — décision 6a explicite (précision du chef)** : le
   libellé actuel (`UnitInfo.label`) est à la fois la clé de référence et la valeur d'affichage,
   **modifiable depuis le backoffice** — ce n'est donc pas un identifiant canonique. Pour 6a,
   trois notions seront distinguées : (a) l'**identité technique** de l'unité (`units.id`,
   stable), (b) un éventuel **code canonique** non localisé (`kg`, `g`… — si le besoin réel le
   justifie), (c) les **libellés d'affichage et traductions** (modifiables, jamais des
   références). Si le libellé peut changer ou être localisé, la référence par libellé ne doit
   pas survivre en l'état : la migration des références existantes (vers `unit_id` ou vers le
   code canonique) sera **justifiée et décrite dans le dossier 6a** — **aucune modification en
   F1** (le moteur et les données actuelles parlent des libellés ; changer la référence
   maintenant serait une migration artificielle).
6. **Réservations email (`emailReservationId` Base64URL)** : la bascule de forme reste
   planifiée et testée — la transformation 6a la conservera (réversible, déjà prouvée).
7. **Identité utilisateur ≠ moyens de connexion — précision conservée pour F4 (demande du
   chef)** : les **coordonnées de contact** (email, téléphone) et les **identités de
   connexion** (email, téléphone, ou fournisseur externe type Google/Apple) ne sont pas
   nécessairement les mêmes notions. Aucune table générique `user_identifiers` ni moteur
   universel d'identifiants n'est créé maintenant — mais **F4** devra permettre de faire
   évoluer le moyen de connexion (ajouter un fournisseur, changer d'email ou de téléphone de
   connexion) **sans modifier l'`uid` ni casser les relations existantes** : l'`uid` reste
   l'ancre de toutes les relations, les identifiants de connexion sont des données évolutives
   rattachées à l'`uid` (avec leurs propres unicités — email déjà garanti, téléphone à
   décider). **Hors périmètre F1** ; conception détaillée au lot F4.

## 7. Conclusion

Aucun modèle existant ne contrevient au principe : les identités techniques sont stables et
immuables, les relations utilisent les ids techniques, les emails/téléphones/slugs restent des
attributs. Les seuls écarts réels (slug de recette et libellé d'unité non garantis par une
contrainte serveur, unicité du téléphone non décidée) sont **notés pour 6a/F4**, ne touchent
pas F1 et n'exigent aucune refonte aujourd'hui.
